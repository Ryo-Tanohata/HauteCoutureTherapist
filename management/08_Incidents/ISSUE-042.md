# ISSUE-042: 「読んでから書き戻すまで」の隙に、もう一方の書き込みが置き場から消える

## 概要
- **発生日**: 2026-08-07（サロンからの指摘ではなく、ISSUE-040 の申し送りを自分で調べて確認）
- **分類**: MINOR（データは失われないが、置き場から一時的に消える）
- **状態**: **未修正（既知・実測済み）**
- **担当**: Claude Code

## どうして調べたか

ISSUE-040（消した記録が復活する）を直したとき、まだ残る隙としてサロンにこう申し送っていた。

> A が読んでから書き戻すまでの数秒に B が書き込むと、A の書き戻しで B のぶんが置き場から消えます（B の端末には残るので、B が次に同期すれば戻ります）。

ISSUE-040 も ISSUE-041 も、**「たぶん大丈夫」と思っていたところが実際には壊れていた**件だった。
この申し送りも見積もりが甘い可能性があるため、**言葉で説明する前に、実際に起こして測った。**

## 症状

同期は ①置き場を読む → ②手元と突き合わせる → ③置き場に書き戻す、の順で動く。
①と③の間に別の端末が書き戻すと、**あとから来た ③ が、その書き込みを置き場から消す。**

| | パソコン（A） | スマホ（B） | 置き場 |
|---|---|---|---|
| ①| 読む | | |
| | | 書いて同期（丸ごと1周） | **B のぶんが入る** |
| ③| 書き戻す | | **B のぶんが消える** |

## 根本原因

置き場への書き戻しが**丸ごと差し替え**で、しかも**読んだときから変わっていないかを確かめていない**。

```js
await fetch(`${base}?what=data`, { method: 'PUT', body: bytes });   // 無条件に上書き
```

①で読んだ内容を土台に作った snapshot を、③でそのまま被せる。
その間に置き場が変わっていても、気付かない（データベースでいう lost update）。

## 実測

`management/09_Verification/verify-lostupdate.js`（同じことを次に確かめられるよう、残した）。
置き場を1つだけ Node 側に置き、実物の `product/index.html` を
2台ぶん開いて触らせる。A の ③ だけを関門で足止めし、その間に B に丸ごと1周させた。
中身は毎回**まっさらな第三の端末を開いて**読み、置き場に本当に何があるかを確かめた。

| 調べたこと | 結果 |
|---|---|
| ふだんの ① → ③ の間隔 | **19〜22ms**（手元の回線なし・データ少）|
| 隙に書き込むと、置き場から消えるか | **消えた**（`["r1","rA"]`。B の `rB` が無い）|
| B の端末には残っているか | **残っていた** |
| B がもう一度同期すると戻るか | **戻った**（`["r1","rA","rB"]`。A のぶんも残った）|
| 隙に「消した」場合、消したものが生き返るか | **生き返らなかった** |

### 隙の広さ

手元では **19〜22ms**。ただしこれは回線が無く、データも少ない状態の値。
実際は ①の返事が届く時間 ＋ 突き合わせ ＋ 暗号化 ＋ ③を送り出す時間なので、
**回線ごしでは往復1回ぶん、おおむね 0.2〜1秒**と見ておくのが妥当。

つまり **「数秒」は言い過ぎだった**（こちらに厳しい方向の誤り）。
同期は保存のたびに走るので、2台で同時に手を動かしていれば当たることはある。

### 消したものは生き返らなかった（ISSUE-040 の直しが効いている）

隙の中で消した場合も試した。E を足止めしている間に F が記録を消して同期し、そのあと E に書き戻させた。
**生き返らなかった。** 墓標（ISSUE-040 で入れた `deletions`）を持っている F 自身が次に同期した時点で、
消えた状態に戻る。ただし E の古い書き戻しは**置き場の墓標も一緒に消す**ため、
その瞬間に別の端末が読むと記録が見えてしまう。F が同期すれば直る。

## なぜ今すぐ直さないか

- **データは失われない。** 消えるのは置き場の側だけで、書いた端末には残る。次の同期で戻る
- 直すには置き場側（`functions/api/sync.js`）に**書き戻しの条件付け**が要る。R2 の ETag を使い、
  「読んだときと変わっていなければ書く、変わっていたら読み直してやり直す」形にする
- **サーバー側の作り替えは、ISSUE-040 の直しがサロンで落ち着いたのを確かめてからにしたい。**
  同期まわりを続けて2度いじると、何が効いたのか分からなくなる

## 直すときの案

1. `functions/api/sync.js` の PUT を `onlyIf: { etagMatches }` にする（R2 が条件付き書き込みを持っている）
2. 端末側は ①の返事の ETag を覚えておき、③に添える
3. 弾かれたら **①からやり直す**（突き合わせは既に項目単位なので、やり直せば両方残る）

これで隙は閉じる。やり直しは1〜2回で収まるはず。

## 申し送り

- **サロンには「置き場が一時的に古く見えることがある」という形で残る。** どちらの端末でも、
  もう一度同期すれば揃う
- 端末の時計が大きくずれていると、新旧の判定そのものが狂う。これは別の話（未着手）
