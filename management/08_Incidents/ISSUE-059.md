# ISSUE-059: 「毎日午前0時に更新」と出ているのに、11日前のまま更新されない

## 概要
- **発生日**: 2026-08-10
- **分類**: MAJOR（表示と実際の食い違い）
- **状態**: **対応済み（案A ＋ 案C）**
- **担当**: Claude Code

## 症状

> 更新が毎日なのになぜ更新されませんか？

星詠みメッセージの画面に、こう出ていました。

```
📅 取得・生成日時: 2026/07/30 22:18
🤖 生成AI: claude (Agent SDK) / claude-sonnet-5
🔄 更新目安: 毎日午前0時に更新
```

その日は **2026/08/10**。**11日ぶんそのまま**でした。

## 根本原因

**「毎日午前0時に更新」は、更新する仕掛けではなく、ただの文字です。**

`server/advice.js` の `getCacheInfo()` が、期間ごとに決まった文字を返しているだけです。

```js
if (period === 'today') {
    return {
        key: `today_${yyyy}-${mm}-${dd}`,
        intervalLabel: '毎日午前0時に更新',   // ← 画面に出る文字。これ自体は何もしない
        periodName: '今日'
    };
}
```

画面（`ui.js`）は、その文字をそのまま出しています。

```js
nextUpdateEl.innerHTML = `🔄 更新目安: <strong>${data.updateInterval || '定期更新'}</strong>`;
```

**では、誰が更新するのか。** 星詠みは**あらかじめ作ってファイルに置く**作りです。
ブラウザは置いてあるファイルを読むだけで、開いてもAIは呼ばれません（そういう設計にしてあります）。

```
定期実行 ── Claude ──▶ product/data/advice/<period>.json ──▶ ブラウザが読む
```

作る側は `scripts/refresh-advice.js`。README にも「毎日1回実行しておけば」と書いてあります。

**その「定期実行」が、どこにも登録されていませんでした。**

- リポジトリに `.gitlab-ci.yml` は**ありません**（`ls` で確認）
- Cloudflare 側で動いているのは `functions/api/sync.js` だけ。時刻で動く仕組みは**ありません**
- `crontab` に入れる例は README に書いてありますが、**書いてあるだけで、登録はされていません**

つまり、こういう連鎖になっていました。

| 段 | 必要なこと | 実際 |
|---|---|---|
| 1 | 誰かが `npm run advice:refresh` を動かす | **誰も動かしていない** |
| 2 | できたファイルをコミットする | （1が無いので発生しない） |
| 3 | main に送って配る | （同上） |

**7/30 22:18 は、最後に手で動かした時刻**です。それ以降、1〜3のどれも起きていません。

### もうひとつ、見落としやすいところ

**手元のPCに cron を仕掛けるだけでは、サロンの画面は変わりません。**
星詠みはファイルとしてリポジトリに入っているので、
**作ったあとコミットして main に送るところまでやらないと配られません。**

「毎日走らせる」と「毎日配る」は別の話です。

## どうやって見つかったか

画面の文字（毎日更新）と、ファイルの中の日付（7/30）が食い違っていたので、
**文字のほうを grep して出どころを追いました。**

```bash
grep -rn "毎日午前0時" --include=*.js .
# → server/advice.js:122  intervalLabel: '毎日午前0時に更新',
```

`intervalLabel` という名前の時点で、**更新する仕掛けではなく貼り紙**だと分かります。
あとは「では実際に更新するのは誰か」を探して、**どこにも居ない**ことを確かめました。

```bash
ls .gitlab-ci.yml .github        # → 無い
grep -rn "cron" --include=*.md . # → README に「例」が書いてあるだけ
```

`npm run advice:status` が、そのまま証拠になりました。

```
today       2026/07/30 22:18     claude (Agent SDK) / claude-sonnet-5 要更新
1week       2026/07/30 22:19     claude (Agent SDK) / claude-sonnet-5 要更新
1month      2026/07/30 22:19     claude (Agent SDK) / claude-sonnet-5 要更新
3months     2026/07/30 22:20     claude (Agent SDK) / claude-sonnet-5 最新
```

**「要更新」と自分で言っているのに、誰もそれを見ていなかった**、という状態です。

## 応急でやったこと（中身の最新化）

期限が切れていた3つ（today / 1week / 1month）を作り直しました。

```
today       2026/08/10 10:12     claude (Agent SDK) / claude-sonnet-5 最新
1week       2026/08/10 10:13     claude (Agent SDK) / claude-sonnet-5 最新
1month      2026/08/10 10:13     claude (Agent SDK) / claude-sonnet-5 最新
```

3months / 6months / 1year は**まだ期限内**なので触っていません（作り直すと文面だけ変わって意味がありません）。

### ここで見つかった、おまけの不具合

**そのまま `npm run advice:refresh` を動かすと、モデルが haiku になります。**

```
[AI] trying provider=claude model=claude-haiku-4-5
```

既存のファイルは全部 `claude-sonnet-5` で作られていました。
`product/js/app/model-registry.js` の並びが「速さ・安さ優先」で
`['claude-haiku-4-5', 'claude-sonnet-5', 'claude-opus-5']` の順になっているためです。

この並びは**フローティングチャット向けに決めたもの**で、
星詠み（1000字を超える読み物）には向きません。ISSUE-055 で
「軽いモデルは渡した条件を守らないことがある」ことを実測しています。

今回は `CLAUDE_MODEL=claude-sonnet-5` を付けて作り直し、既存と揃えました。
**自動更新を入れるなら、ここも一緒に決める必要があります**（下の案に含めます）。

## 直しかたの案（未実施・ご判断ください）

### 案A：更新する文字を、実際に合わせる（いちばん小さい）

「毎日午前0時に更新」を「**手動更新**」などに変え、
最終生成から日が経っていたら画面に印を出す。

- ✅ 嘘をつかなくなる。**今日すぐできる**
- ❌ 更新は相変わらず手作業のまま

### 案B：GitLab の定期パイプラインで、毎日作って自動でコミットする

GitLab の Schedules（無料枠にあります）で毎日1回動かす。

- ✅ **本当に毎日更新される。** 配るところまで自動
- ❌ **Claude のログインが CI では使えません。** Agent SDK は「このPCのログイン」なので、
  CI で動かすには `ANTHROPIC_API_KEY`（従量課金のAPIキー）が要ります
- ❌ CI に鍵を1本置くことになります（ISSUE-049 で挙げた「鍵の持ち方」の話が1つ増えます）
- 費用の目安：星詠み6期間ぶんで1日あたり数円程度。ただし**毎日走ります**

### 案C：サロンのPCで毎日動かし、送るところまで自動にする

Windows のタスクスケジューラに、こういう1行を登録する。

```
npm run advice:refresh && git add product/data/advice && git commit -m "..." && git push
```

- ✅ **鍵が要りません。** いまのプラン枠のまま動きます（費用も増えません）
- ✅ Agent SDK がそのまま使えるので、モデルも今のまま選べます
- ❌ **PCが起きていないと動きません。** 消えている日は飛びます
- ❌ 自動で `git push` が走る形になります。設定を一度きちんと作る必要があります

### 案D：更新を諦めず、押せるようにする

「いま作り直す」ボタンをローカル起動時だけ出す。

- ✅ 見たときに気づいて、その場で直せる
- ❌ **閲覧者の操作でAIが動く形は避ける**と決めてあります（README の境界）。
  ローカル限定に閉じる作りが要るので、見た目より手間がかかります

### お勧め（→ サロンのご判断で **A ＋ C** に決定。下の「直したこと」へ）

**A ＋ C** です。

まず A で**画面が嘘をつくのをやめる**（今日できます）。
そのうえで C なら**鍵を増やさずに**自動化できます。ISSUE-049 で
「AIの鍵が端末に平文で残る」ことを課題に挙げている以上、
B のように**新しい鍵を1本増やす**のは、それだけの理由が要ると考えます。

C が「PCが消えている日は飛ぶ」のは弱点ですが、
A で**古いときに印が出る**ようにしておけば、飛んだことには気づけます。

## 直したこと

### 案A：画面が、実際に最新かどうかを言うようにした

**「更新目安」という言葉をやめました。** そう更新されているように読めるためです。
表示は「**更新サイクル**」に改め、**別の行で、いま最新かどうかを言う**ようにしました。

| 状態 | 出るもの |
|---|---|
| 期限内 | `✅ 最新です` |
| 期限切れ | `⚠️ 更新サイクルを 11日 過ぎています。`＋作り直しかた |
| 判断できない | **何も出さない** |

3つめが大事なところです。この項目を持たない古いファイルでは、**黙ります。**
**分からないのに「最新です」と言うほうが、害が大きい**ためです。

#### 判定を、ブラウザに書き写さなかった

期間ごとの更新サイクルの決め方は `server/advice.js` の `getCacheInfo()` にあります。
同じ規則をブラウザ側にもう一度書くと、**片方だけ直したときに静かにずれます。**

そこで、**サイクルの終わる時刻を生成側が入れて配る**ようにしました。

```js
// このサイクルが終わる時刻。ブラウザはこれを見て「古い」と出す。
nextUpdateAtISO: ...
```

その時刻自体も、規則を書き写さずに求めています。
**世代キーが変わる最初の日を、前から1日ずつ探します。**

```js
function nextCycleStart(period, date = new Date()) {
    const key = getCacheInfo(period, date).key;
    const d = new Date(date.getFullYear(), date.getMonth(), date.getDate());
    for (let i = 0; i < 400; i++) {
        d.setDate(d.getDate() + 1);
        if (getCacheInfo(period, d).key !== key) return new Date(d);
    }
    return null;
}
```

遠回りに見えますが、**サイクルの決め方を変えても、直すのは `getCacheInfo` の1か所で済みます。**
1年ぶんでも高々366回なので、速さは問題になりません。

既にあった6つのファイルには、`--backfill`（AIを呼ばない）で後から足しました。
**文章を作り直さずに、期限だけを入れられます。**

```
[FILL] today: 追加項目 nextUpdateAtISO
...
today     2026/08/10 10:12 → 2026-08-11T00:00:00.000Z
1year     2026/07/30 22:21 → 2027-01-01T00:00:00.000Z
```

あわせて、この帯で出していた**生成AI名と生成日時を escapeHtml に通しました**（ISSUE-043 の続き）。

### 案C：サロンのパソコンで、毎日ひとりでに更新する

`scripts/daily-advice.ps1`（Windows）と `scripts/daily-advice.sh`（Mac / Linux）を足しました。
**作る → コミット → 送る**を1本にしてあります。3つ揃って初めて画面が変わるためです。

タスクスケジューラへの登録手順は `management/10_Operations/星詠みの毎日更新.md`。

**わざと止める作りにしてあります。**

| 状態 | どうなるか |
|---|---|
| `main` 以外の枝に居る | **何もせずに止まる**（作業中の枝に積まないため） |
| 取り込みでぶつかった | **作らずに止まる** |
| 更新サイクルの中だった | 作らずに終わる（正常） |
| 送信が回線で落ちた | 2・4・8・16秒と間を空けて4回まで試す |

コミットするのは `product/data/advice` の下だけです。
**書きかけのものを巻き込みません。**

登録には `-StartWhenAvailable` を付けています。
**6時にパソコンが消えていても、次に起きたときに動きます。**

モデルは `CLAUDE_MODEL=claude-sonnet-5` を明示しています。
既定のままだと haiku になってしまうためです（上記）。

## 検証結果

`management/09_Verification/verify-advice-freshness.js`

```
=== 1. 期限内なら「最新です」と出るか
    {"fresh":"✅ 最新です","shown":true,"cycle":"🔄 更新サイクル: 毎日午前0時に更新"}
=== 2. 期限を過ぎたら、過ぎたと言うか（ISSUE-059 の状態を再現）
    {"fresh":"⚠️ 更新サイクルを 11日 過ぎています。…","shown":true}
=== 3. 期限の項目が無い古いファイルでは、黙るか
    {"fresh":"","shown":false}
=== 4. 配ってあるファイルが、実際に期限を持っているか
  nextUpdateAtISO がある: ✅ 2026-08-11T00:00:00.000Z
  ぜんぶ通りました
```

**新しいときと古いときの両方を見ています。** 片方だけでは、
「いつも最新ですと出す」実装でも通ってしまうためです。
古い側は、サロンが実際に見た**11日遅れの状態を作って**確かめました。

自動更新のほうは、**枝を合わせて実際に1周させました**（作成→コミット→送信）。
`main` 以外に居るときに止まることも、その場で確かめています。

## 申し送り

- **パソコンが何日も消えていれば、そのぶん更新されません。** 仕組み上避けられないので、
  案Aの印（`⚠️ 更新サイクルを N日 過ぎています`）で**気づける**ようにしてあります
- **README の「毎日1回実行しておけば」は、実行する人が居ることが前提**でした。
  いまは登録手順を `10_Operations` に置いてあります
- **`npm run advice:refresh` はモデルを haiku で選びます。** 当面は
  `CLAUDE_MODEL=claude-sonnet-5` を付けて動かしてください
- 「更新目安」の文字は `server/advice.js` の `getCacheInfo()` 1か所です。
  直すならそこだけで済みます
